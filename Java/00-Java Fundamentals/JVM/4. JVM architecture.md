
> [!abstract] Main Idea
> **The JVM is not simply "a virtual machine that runs Java code."** It is an abstract machine that:
>
> 1. loads `.class` files;
> 2. verifies, links, and initializes classes;
> 3. provides runtime memory areas;
> 4. executes JVM bytecode;
> 5. may compile frequently executed bytecode into native machine code;
> 6. manages memory and garbage collection;
> 7. can interact with native code through JNI.
>
> **Important:** the JVM Specification describes an **abstract machine**, not a specific implementation such as HotSpot. Details such as the exact memory layout, garbage collector, and bytecode-to-machine-code compilation strategy are implementation-specific.

---

A useful mental model is:

│                                                               │
│  ┌───────────────────────┐     ┌───────────────────────────┐  │

│  │ Subsystem             │     │                           │  │
│  │                       │     │ Heap                      │  │
│  │ Loading               │     │ Method Area               │  │

│              │                 │ Native Method Stacks      │  │

│              ▼                              │                 │

* **JNI / Native Interface** → connects Java code with native code.

# 4.2 Class Loader Subsystem

## 4.2.1 What Is a Class Loader?

A `ClassLoader` is the mechanism responsible for loading the binary representation of a class or interface and making it available to the JVM.

For example:

```java
UserService service = new UserService();
```

At some point the JVM needs the binary representation of:

```text
com/example/UserService.class
```

Conceptually:

```text
"com.example.UserService"
          │
          ▼
      ClassLoader
          │
          ▼
   binary representation
          │
          ▼
     runtime class
```

The JVM Specification does **not** require every class to come from a physical `.class` file. A class loader can obtain class bytes from many different sources.

Examples:

```text
filesystem
JAR
network
database
generated byte[]
encrypted storage
```

### Important

A `ClassLoader` **does not execute Java bytecode**.

Its responsibility is to load and define classes.

Execution is handled later by the execution engine.

---

# 4.2.2 Class Lifecycle

The class lifecycle can be visualized as:

```text
           Loading
              │
              ▼
           Linking
        ┌─────┼─────┐
        │     │     │
     Verify Prepare Resolve
        │     │     │
        └─────┼─────┘
              │
              ▼
        Initialization
              │
              ▼
       Class is usable
```

The JVM Specification formally describes:

```text
Loading
Linking
Initialization
```

and:

```text
Linking
 ├── Verification
 ├── Preparation
 └── Resolution
```

Resolution does not necessarily have to happen immediately. The JVM implementation has some freedom regarding when symbolic references are resolved.

---

# 4.2.3 Loading

**Loading** means finding the binary representation of a class or interface and creating its runtime representation.

Conceptually:

```text
String class name
       │
       ▼
ClassLoader
       │
       ▼
find class bytes
       │
       ▼
define class
       │
       ▼
Class object
```

For example:

```java
Class<?> clazz = Class.forName("com.example.User");
```

Conceptually:

```text
"com.example.User"
        ↓
ClassLoader
        ↓
class bytes
        ↓
defineClass(...)
        ↓
Class<User>
```

The exact mechanics depend on the class loader implementation.

---

# 4.2.4 Built-in Class Loaders

Modern Java has three important built-in class loaders:

```text
Bootstrap Class Loader
        │
        ▼
Platform Class Loader
        │
        ▼
System / Application Class Loader
```

They serve different purposes.

---

## Bootstrap Class Loader

The **Bootstrap Class Loader** is the fundamental class loader built into the JVM.

It loads core platform classes such as:

```text
java.lang.Object
java.lang.String
java.lang.Class
...
```

A key detail:

```java
String.class.getClassLoader()
```

returns:

```text
null
```

This does **not** mean `String` was not loaded by a class loader.

It means the class was loaded by the **bootstrap class loader**, which is represented specially rather than as an ordinary Java `ClassLoader` object.

---

## Platform Class Loader

The **Platform Class Loader** loads platform classes that are not part of the bootstrap set.

It can be obtained with:

```java
ClassLoader.getPlatformClassLoader();
```

It represents the platform-level class-loading layer in modern modular Java.

---

## System / Application Class Loader

The **System Class Loader**, also called the **Application Class Loader**, is the loader normally used to load application classes.

It can be obtained with:

```java
ClassLoader.getSystemClassLoader();
```

This is usually the loader involved in loading classes from the application's classpath/module path.

---

# 4.2.5 Parent Delegation Model

A standard class-loading hierarchy looks like:

```text
          Bootstrap
              ▲
              │
          Platform
              ▲
              │
      Application
              ▲
              │
       Custom Loader
```

When a custom class loader is asked to load a class, the usual delegation sequence is conceptually:

```text
Custom ClassLoader
       │
       ├── already loaded?
       │
       ├── parent.loadClass(...)
       │
       └── findClass(...)
```

So the child usually gives the parent a chance first.

If the parent cannot load the class:

```text
parent fails
     ↓
findClass()
     ↓
child tries
```

This is the **parent delegation model**.

---

# 4.2.6 Why Does Parent Delegation Exist?

It prevents different class loaders from independently defining critical platform classes.

Imagine:

```text
Bootstrap → java.lang.String #1

CustomLoader → java.lang.String #2
```

If arbitrary application class loaders could freely replace core platform classes, the JVM's type system and security model would become much harder to reason about.

Parent delegation helps ensure that core classes are loaded by the appropriate higher-level class loaders.

---

# 4.2.7 Class Identity

One of the most important JVM concepts:

> A class is identified not only by its binary name, but also by the class loader that defines it.

Conceptually:

```text
Class identity =
    binary name
    +
    defining class loader
```

Therefore:

```text
com.example.User
    loaded by LoaderA

com.example.User
    loaded by LoaderB
```

may represent **two different runtime types**.

So you can have:

```text
same package
same class name
same bytecode
```

but still get type incompatibility because the defining class loaders are different.

This is one of the key reasons class loaders matter in:

* application servers;
* plugin systems;
* modular systems;
* hot-reload environments.

---

# 4.2.8 Linking

After loading, the class must be linked.

```text
Loading
   ↓
Linking
```

Linking consists of:

```text
Verification
Preparation
Resolution
```

---

## Verification

The JVM checks that the class file and bytecode are structurally and semantically valid according to JVM rules.

Conceptually:

```text
class file
    ↓
bytecode verifier
    ↓
valid?
```

The goal is to reject malformed or invalid bytecode before unsafe execution.

---

## Preparation

During preparation, the JVM creates the runtime structures required by the class and prepares storage for static fields.

For example:

```java
class Config {
    static int x = 10;
}
```

Preparation is conceptually concerned with:

```text
class structure
static storage
default state
```

Do not confuse this with initialization.

```text
Preparation
    ↓
storage and default state

Initialization
    ↓
execute class initialization logic
```

---

## Resolution

Class files contain **symbolic references**.

For example, bytecode can refer symbolically to:

```text
SomeClass.someMethod()
```

rather than storing a final machine address.

Resolution connects those symbolic references to runtime entities.

Conceptually:

```text
symbolic reference
        ↓
     resolve
        ↓
runtime class / field / method
```

A particularly important point is that resolution does not necessarily happen eagerly. The JVM specification allows symbolic references to be resolved at different points depending on implementation and use.

---

# 4.2.9 Initialization

Initialization is different from loading and linking.

Initialization means executing the class initialization method:

```text
<clinit>
```

For example:

```java
class Config {

    static int x = 10;

    static {
        System.out.println("initialized");
    }
}
```

The compiler translates the static initialization logic into `<clinit>`.

Conceptually:

```text
<clinit>:
    x = 10
    println(...)
```

When the class is initialized, JVM executes that initialization logic.

A useful mental distinction:

```text
Loading
    ↓
"I know what this class is."

Linking
    ↓
"I have verified and prepared it."

Initialization
    ↓
"I have executed its static initialization."
```

---

# 4.2.10 Runtime Data Areas

The JVM Specification defines several runtime data areas.

They can be divided into:

```text
Shared by all threads
        │
        ├── Heap
        ├── Method Area
        └── Runtime Constant Pool
```

and:

```text
Per-thread
        │
        ├── PC Register
        ├── JVM Stack
        └── Native Method Stack
```

Important:

> The JVM Specification defines the semantics of these areas, but the exact physical implementation is implementation-specific.

---

# 4.3 Heap

The **heap** is the runtime area from which memory for:

```text
objects
arrays
```

is allocated.

For example:

```java
User user = new User();
```

Conceptually:

```text
Stack
 │
 │ user
 ▼
┌───────────────┐
│ User object   │
│ id = 10       │
│ name = ...    │
└───────────────┘
       Heap
```

The heap is:

```text
shared between threads
```

and is the primary memory area managed by automatic memory management.

The JVM Specification guarantees the existence of the heap, but does not mandate one specific heap layout or garbage collector.

---

# 4.3.1 Heap and Garbage Collection

A common mistake is to think:

```text
GC = memory area
```

It is not.

The GC is a **memory management mechanism**.

Conceptually:

```text
reachable objects
        │
        │
unreachable objects
        │
        ▼
       GC
        │
        ▼
 memory reclaimed
```

Different JVM implementations can provide different collectors.

For example, HotSpot has supported collectors such as:

```text
Serial GC
Parallel GC
G1
ZGC
Shenandoah
```

The exact set depends on the JVM distribution and version.

The important distinction is:

```text
Heap
    = memory area

GC
    = mechanism managing that memory
```

---

# 4.4 Method Area

The **Method Area** is a shared runtime area containing per-class and per-interface structures.

Conceptually, it contains information such as:

```text
class metadata
method information
field information
runtime constant pool
method code
constructor information
```

The JVM Specification defines the Method Area as an abstract runtime concept.

Do **not** automatically equate it with:

```text
Method Area == Metaspace
```

That is incorrect.

Instead:

```text
JVM Specification
        │
        ▼
   Method Area
        │
        ▼
abstract concept
```

while:

```text
HotSpot
   │
   ▼
Metaspace
```

is a specific implementation choice.

This distinction is very important in JVM interviews.

---

# 4.5 Runtime Constant Pool

Every class file contains a constant pool.

After the class is loaded, the JVM has a corresponding **runtime constant pool**.

It contains symbolic and constant information used at runtime, including references related to:

```text
classes
fields
methods
strings
method handles
method types
dynamic constants
```

The runtime constant pool is closely connected to:

```text
symbolic linking
dynamic linking
method invocation
constant resolution
```

Conceptually:

```text
.class
 └── constant_pool
          │
          ▼
       runtime
          │
          ▼
Runtime Constant Pool
```

---

# 4.6 JVM Stack

Each JVM thread has its own **JVM Stack**.

```text
Thread 1
 └── JVM Stack

Thread 2
 └── JVM Stack

Thread 3
 └── JVM Stack
```

Therefore:

```text
JVM Stack = per-thread
```

Unlike the heap, it is not shared between threads.

---

# 4.6.1 Frames

Every method invocation creates a **frame**.

Suppose:

```java
main()
   ↓
foo()
   ↓
bar()
```

The stack can be visualized as:

```text
JVM Stack

┌──────────────┐
│ bar frame    │ ← top
├──────────────┤
│ foo frame    │
├──────────────┤
│ main frame   │
└──────────────┘
```

When a method finishes, its frame is removed.

---

# 4.6.2 What Does a Frame Contain?

A frame contains information conceptually including:

```text
Local Variables
Operand Stack
Reference to Runtime Constant Pool
```

A frame may also contain implementation-specific information.

---

## Local Variables

The local variable array is used for:

```text
method parameters
local variables
intermediate values
```

For example:

```java
int add(int a, int b) {
    int c = a + b;
    return c;
}
```

Conceptually:

```text
Local Variables

slot 0 → this / a
slot 1 → b
slot 2 → c
```

The exact slot layout is defined by the JVM execution model.

---

# 4.6.3 Operand Stack

The JVM is a **stack-based virtual machine**.

For example:

```java
int c = a + b;
```

can be represented by bytecode conceptually similar to:

```text
load a
load b
add
store c
```

The idea is:

```text
load a
   ↓
operand stack

load b
   ↓
operand stack

add
   ↓
result

store c
```

This is one of the fundamental characteristics of JVM bytecode.

---

# 4.6.4 Why Can StackOverflowError Happen?

Consider:

```java
void f() {
    f();
}
```

Each recursive invocation creates another frame:

```text
f
f
f
f
f
f
...
```

Eventually, the JVM can no longer create another stack frame.

The result is:

```text
StackOverflowError
```

So:

```text
method recursion
      ↓
more frames
      ↓
stack exhausted
      ↓
StackOverflowError
```

---

# 4.6.5 Stack vs Heap

A common beginner rule is:

> "Primitives are on the stack and objects are on the heap."

That is too simplistic.

A better mental model is:

```text
Stack:
    method execution state
    frames
    local variables
    operand stacks

Heap:
    objects
    arrays
```

For example:

```java
User user = new User();
```

Conceptually:

```text
Stack
┌──────────────────────┐
│ reference: user ──────────────┐
└──────────────────────┘        │
                                ▼
                            Heap
                        ┌───────────────┐
                        │ User object   │
                        └───────────────┘
```

However, JIT optimizations can change the physical implementation of allocations. The conceptual model should not be confused with a guarantee about physical memory placement.

---

# 4.7 PC Register

Every JVM thread has its own **program counter (`pc`) register**.

Conceptually:

```text
Thread
  │
  └── PC → current JVM instruction
```

It represents the current execution position for the thread.

If the current method is native, the JVM specification does not define the PC value in the same way; it is effectively not meaningful there.

---

# 4.8 Native Method Stack

The JVM also defines a **Native Method Stack** for the execution of native methods.

Conceptually:

```text
Java code
    ↓
native method
    ↓
C / C++
    ↓
OS / hardware
```

The exact implementation of native method stacks is not mandated by the JVM Specification.

---

# 4.9 Execution Engine

Now we reach the component that actually executes the bytecode.

> **The Class Loader loads classes. Runtime Data Areas store runtime state. The Execution Engine executes the code.**

However, an important distinction must be kept in mind:

```text
JVM Specification
```

versus:

```text
specific implementation, e.g. HotSpot
```

The specification does not say:

> "Every JVM must contain Interpreter + C1 + C2."

Those are implementation details.

---

# 4.9.1 Interpreter

One way to execute bytecode is through an interpreter:

```text
bytecode
   ↓
Interpreter
   ↓
execute instruction
   ↓
next instruction
```

The interpreter reads JVM instructions and executes them.

Advantages:

```text
fast startup
no need to compile all code before execution
```

Disadvantage:

```text
repeated interpretation can be less efficient
for frequently executed code
```

This leads naturally to JIT compilation.

---

# 4.9.2 JIT Compiler

JIT means:

> **Just-In-Time compilation**

The idea is:

```text
bytecode
   ↓
execution
   ↓
profiling
   ↓
hot code detected
   ↓
JIT compilation
   ↓
native machine code
```

Suppose a method is executed millions of times.

The JVM may determine:

```text
this method is hot
```

and compile it into native machine code.

Then future executions can use the compiled version.

---

# 4.9.3 Why "Just-In-Time"?

Because compilation happens:

```text
while the program is running
```

not entirely before the program starts.

Compare:

```text
Traditional ahead-of-time style

source
  ↓
compiler
  ↓
machine code
  ↓
run
```

with a typical HotSpot-style flow:

```text
source
  ↓
bytecode
  ↓
JVM startup
  ↓
interpret / execute
  ↓
collect profiling information
  ↓
compile hot code
  ↓
optimized machine code
```

---

# 4.9.4 Adaptive Optimization

JIT compilation becomes especially powerful because the JVM can observe the running application.

Conceptually:

```text
run program
     ↓
collect profile information
     ↓
detect hot spots
     ↓
compile important methods
     ↓
optimize based on observed behavior
```

This is often called **adaptive optimization**.

Instead of optimizing blindly, the runtime can use actual execution data.

---

# 4.9.5 C1 and C2

HotSpot traditionally uses tiered compilation with **C1** and **C2** compilers.

Conceptually:

```text
          Bytecode
             │
             ▼
        Interpreter
             │
         profiling
             │
             ▼
           C1
     faster compilation
             │
       more profiling
             │
             ▼
           C2
    aggressive optimization
```

### C1

C1 is optimized for:

```text
fast compilation
lower compilation overhead
quick performance improvements
```

### C2

C2 is designed for:

```text
more aggressive optimization
higher peak performance
```

The exact compiler architecture is specific to HotSpot, not a universal JVM requirement.

---

# 4.9.6 Inlining

One of the most important JIT optimizations is **method inlining**.

Suppose:

```java
int square(int x) {
    return x * x;
}
```

and:

```java
int result = square(10);
```

The JIT may transform the compiled representation conceptually into something like:

```text
result = 10 * 10
```

instead of keeping the method call.

This can remove call overhead and enable further optimizations.

Important:

> The JIT is not modifying your Java source code. It is optimizing the runtime compiled representation.

---

# 4.9.7 Deoptimization

JIT optimizations are often based on runtime assumptions.

For example:

```text
"this type is almost always used here"
"this branch is almost never taken"
"this call always goes to this implementation"
```

But assumptions can become invalid.

Then:

```text
optimized machine code
        ↓
assumption becomes false
        ↓
deoptimization
        ↓
return to a safer execution path
```

This means JVM optimizations are not necessarily permanent.

The JVM can:

```text
optimize
    ↓
discover assumption is wrong
    ↓
deoptimize
    ↓
continue execution safely
```

---

# 4.9.8 Garbage Collector

The garbage collector finds objects that are no longer reachable and reclaims their memory.

A conceptual model:

```text
GC Roots
   │
   ▼
reachable objects
   │
   ├── A
   ├── B
   └── C

unreachable objects
   │
   ├── X
   ├── Y
   └── Z

        ↓
       GC
        ↓
memory for X/Y/Z reclaimed
```

The JVM Specification does **not** define one concrete GC algorithm.

That is a JVM implementation detail.

---

# 4.10 JNI — Java Native Interface

**JNI = Java Native Interface**

JNI is the standard interface between Java code and native code.

```text
Java
  │
  ▼
JNI
  │
  ▼
C / C++
  │
  ▼
OS / native libraries
```

JNI is useful when Java needs to interact with:

```text
existing native libraries
operating system APIs
hardware
native system interfaces
performance-sensitive native algorithms
legacy native code
```

---

# 4.10.1 `native` Method

Java provides the keyword:

```java
native
```

For example:

```java
public native int calculate(int x);
```

This means:

> The method is declared in Java, but its implementation exists in native code rather than Java bytecode.

You may also see:

```java
static {
    System.loadLibrary("native_math");
}
```

which loads a native library.

---

# 4.10.2 Native Libraries

Depending on the operating system, a native library might look like:

```text
Linux    → libnative_math.so
Windows  → native_math.dll
macOS    → libnative_math.dylib
```

The JVM loads the native library and establishes the connection between the Java method and native implementation.

---

# 4.10.3 How a Native Call Works

Conceptually:

```text
Java method call
      │
      ▼
native method
      │
      ▼
JNI
      │
      ▼
native function
      │
      ▼
C / C++
      │
      ▼
OS / native library
```

The actual implementation details depend on the JVM and platform.

---

# 4.10.4 `JNIEnv`

A key JNI concept is:

```text
JNIEnv*
```

Conceptually:

```text
JNIEnv*
   │
   ▼
JNI function table
   │
   ├── FindClass
   ├── GetMethodID
   ├── CallObjectMethod
   ├── NewObject
   ├── Throw
   ├── GetFieldID
   └── ...
```

`JNIEnv` gives native code access to the JNI API.

It is associated with the current Java thread.

A native function normally receives access to this interface through its JNI call context.

---

# 4.10.5 JNI References

Native code interacts with Java objects through JNI references.

It should **not** simply assume that a Java object is an ordinary C/C++ pointer whose representation can be freely manipulated.

JNI provides controlled references such as:

```text
Local References
Global References
```

This abstraction allows the JVM to control object representation and garbage collection safely.

---

# 4.10.6 JNI and Exceptions

Native code can also interact with Java exceptions.

Conceptually:

```text
native code
    │
    ▼
detect error
    │
    ▼
JNI Throw / ThrowNew
    │
    ▼
Java exception state
```

This allows native code to report errors back into Java execution.

---

# 4.10.7 JNI Type Mapping

JNI defines native representations for Java primitive types:

| Java      | JNI        |
| --------- | ---------- |
| `boolean` | `jboolean` |
| `byte`    | `jbyte`    |
| `char`    | `jchar`    |
| `short`   | `jshort`   |
| `int`     | `jint`     |
| `long`    | `jlong`    |
| `float`   | `jfloat`   |
| `double`  | `jdouble`  |

Conceptually:

```text
Java int
    ↓
jint
    ↓
C / C++
```

# 4.11 Complete Class Execution Flow

Let's combine everything.

Consider:

```java
public class Main {

    static {
        System.out.println("init");
    }

    public static void main(String[] args) {
        User user = new User();
        user.sayHello();
    }
}
```

---

## Step 1 — Compilation

```text
Main.java
    │
    ▼
javac
    │
    ▼
Main.class
User.class
```

The `.class` files contain JVM bytecode.

---

## Step 2 — JVM Startup

The JVM starts, establishes the required runtime environment, loads the initial class/interface, and eventually invokes:

```java
main(String[])
```

# 4.14 JVM Specification vs HotSpot

This distinction is extremely important.

| Concept                     | JVM Specification | HotSpot                        |
| --------------------------- | ----------------- | ------------------------------ |
| Heap                        | ✅ Defined         | Specific layout/implementation |
| Method Area                 | ✅ Defined         | Specific implementation        |
| JVM Stack                   | ✅ Defined         | Specific implementation        |
| Frame                       | ✅ Defined         | Specific implementation        |
| Bytecode                    | ✅ Defined         | ✅                              |
| Class loading semantics     | ✅ Defined         | Specific implementation        |
| Verification                | ✅ Defined         | Specific implementation        |
| Garbage collector algorithm | ❌ Not fixed       | ✅                              |
| Metaspace                   | ❌                 | ✅                              |
| C1/C2                       | ❌                 | ✅                              |
| Tiered compilation          | ❌                 | ✅                              |
| Specific JIT optimizations  | ❌                 | ✅                              |
| Object layout               | ❌                 | ✅                              |
| Compressed Oops             | ❌                 | ✅                              |

### Golden rule

> Do not say **"the JVM does X"** when X is actually a specific implementation detail of **HotSpot**.

The JVM Specification deliberately leaves some implementation choices open, including:

```text
memory layout
garbage collection
bytecode execution strategy
translation to machine code
```

# 4.15 Common Interview Traps

## Trap 1 — "Heap = all JVM memory"

Incorrect.

The Java process can use memory for many things:

```text
Java Heap
Metaspace
Code Cache
Thread Stacks
Native memory
GC structures
JNI allocations
JVM internal structures
...
```

The heap is only one runtime memory area.

---

## Trap 2 — "Method Area = Metaspace"

Incorrect.

```text
Method Area
```

is a JVM specification concept.

```text
Metaspace
```

is a HotSpot implementation detail.

---

## Trap 3 — "Every `new` always means a physical object allocation on the heap"

Too simplistic.

The conceptual JVM model says:

```text
new object
    ↓
heap
```

But JIT optimizations may eliminate or transform some allocations.

Escape analysis and related optimizations can affect how objects are physically represented at runtime.

Therefore, the specification-level mental model should not be confused with the exact machine-level implementation.

---

## Trap 4 — "The JVM always interprets bytecode"

Incorrect.

A JVM may:

```text
interpret
   ↓
profile
   ↓
JIT compile
   ↓
execute optimized machine code
```

---

## Trap 5 — "The JVM compiles everything before execution"

Also incorrect.

A HotSpot-style JVM may start by interpreting and only later compile frequently executed code.

---

## Trap 6 — "ClassLoader only loads `.class` files from disk"

Incorrect.

A class loader deals with the binary representation of classes and can obtain it from many sources.

---

## Trap 7 — "ClassLoader = JVM"

Incorrect.

```text
JVM
 ├── Class Loading
 ├── Runtime Data Areas
 ├── Execution
 ├── Garbage Collection
 └── Native Integration
```

Class loading is only one part of the JVM.

---

## Trap 8 — "`getClassLoader()` returning `null` means the class wasn't loaded"

Incorrect.

For example:

```java
String.class.getClassLoader()
```

returns `null` because `String` is loaded by the **bootstrap class loader**.

# 4.17 One-Line Summary of Every Component

| Component                 | Remember                                     |
| ------------------------- | -------------------------------------------- |

| **Local Variables**       | Parameters and local values                  |

| **Native Method Stack**   | Native method execution                      |

| **JIT**                   | Compiles hot code                            |

| **JNI**                   | Java ↔ native bridge                         |
| **JNIEnv**                | Native interface for the current thread      |
