# 2. Java Execution Pipeline

The **Java execution pipeline** describes what happens to Java source code from the moment we write a `.java` file until the program executes on the CPU.

The simplified pipeline is:

```text
.java
  │
  │ javac
  ▼
.class
  │
  │ ClassLoader
  ▼
JVM
  │
  ├── Verification
  ├── Linking
  ├── Initialization
  │
  ▼
Bytecode execution
  │
  ├── Interpreter
  │
  └── JIT Compiler
          │
          ▼
    Native machine code
          │
          ▼
         CPU
```

---

## 1. Writing Java source code

We start with a `.java` file.

```java
public class Main {

    public static void main(String[] args) {
        int result = 10 + 20;
        System.out.println(result);
    }
}
```

The file contains **Java source code**.

At this point, the CPU cannot execute it directly.

The CPU understands machine instructions, not Java syntax.

---

# 2. Compilation

We compile the source code using the Java compiler:

```bash
javac Main.java
```

The compiler is usually called **`javac`**.

It performs several tasks, including:

- parsing the source code
    
- checking syntax
    
- checking types
    
- resolving references
    
- generating JVM bytecode
    

The result is usually:

```text
Main.java
    ↓
  javac
    ↓
Main.class
```

The `.class` file contains **JVM bytecode**.

---

# 3. What is inside `.class`?

A `.class` file is not simply "Java code in binary form."

It has a specific structure defined by the **JVM Specification**.

It contains information such as:

- class metadata
    
- superclass information
    
- interfaces
    
- fields
    
- methods
    
- method bytecode
    
- constant pool
    
- attributes
    

Conceptually:

```text
Main.class
│
├── Class information
├── Constant Pool
├── Fields
├── Methods
│    └── Bytecode
└── Attributes
```

The JVM understands this format.

---

# 4. Running the program

We start the application with:

```bash
java Main
```

Notice that we normally write:

```bash
java Main
```

not:

```bash
java Main.class
```

The `java` command starts the JVM and tells it which class contains the entry point.

The JVM then begins loading and preparing the required classes.

```text
java Main
   │
   ▼
JVM starts
   │
   ▼
Load Main
   │
   ▼
Prepare / link / initialize
   │
   ▼
Invoke main()
```

---

# 5. Class Loading

Before the JVM can execute a class, it must load the class into the runtime.

The JVM uses **Class Loaders** for this.

```text
Main.class
    │
    ▼
ClassLoader
    │
    ▼
Class loaded into JVM
```

The class loading process is more than simply reading bytes from disk.

A simplified lifecycle is:

```text
Loading
   ↓
Linking
   ├── Verification
   ├── Preparation
   └── Resolution
   ↓
Initialization
```

This topic deserves its own section:

`[[Class Loading]]`

---

# 6. Bytecode Verification

After loading, the JVM can verify the bytecode.

The verifier checks that the bytecode satisfies JVM constraints.

For example, it helps ensure that:

- instructions are structurally valid
    
- types are used correctly
    
- operands have appropriate types
    
- control flow follows JVM rules
    
- the bytecode does not violate certain JVM safety constraints
    

Conceptually:

```text
.class
   ↓
Loading
   ↓
Verification
   ↓
Valid bytecode
```

This is one of the mechanisms that allows the JVM to safely execute bytecode.

---

# 7. Linking

After loading, the class is linked.

Linking consists of three conceptual phases:

```text
Linking
│
├── Verification
├── Preparation
└── Resolution
```

### Verification

Checks the validity of the bytecode.

### Preparation

The JVM prepares the memory needed for class-level structures and initializes certain static fields to their default values.

For example:

```java
static int count = 10;
```

During preparation, the static field initially receives its default value:

```text
count = 0
```

The assignment:

```text
count = 10
```

happens later during **initialization**.

This distinction is important.

### Resolution

Symbolic references in the constant pool may be resolved to concrete runtime references.

Resolution can occur lazily depending on the JVM implementation.

---

# 8. Class Initialization

After loading and linking, the class may need to be initialized.

For example:

```java
class User {

    static int count = 10;

    static {
        System.out.println("Initializing User");
    }
}
```

During initialization, the JVM executes the class initialization method:

```text
<clinit>
```

Conceptually:

```text
Loading
   ↓
Linking
   ↓
Initialization
   ↓
Class ready for execution
```

Initialization is different from loading.

```text
Loading
→ JVM obtains the class representation

Initialization
→ JVM executes class initialization logic
```

---

# 9. Finding `main()`

For a traditional Java application launched with:

```bash
java Main
```

the JVM needs to invoke:

```java
public static void main(String[] args)
```

Conceptually:

```text
Main.class
    ↓
Class loaded
    ↓
Main initialized
    ↓
main()
    ↓
Application starts
```

`main()` is therefore an **entry point of the application**, not the point where the JVM itself starts.

The JVM starts before `main()` is invoked.

---

# 10. Bytecode Execution

Once the JVM starts executing methods, it needs to execute JVM bytecode.

There are two important concepts:

```text
Interpreter
JIT Compiler
```

A simplified model is:

```text
             Bytecode
                 │
                 ▼
            Interpreter
                 │
                 ▼
         Runtime execution
                 │
         ┌───────┴───────┐
         │               │
         ▼               ▼
   cold code          hot code
                         │
                         ▼
                       JIT
                         │
                         ▼
                Native machine code
```

---

# 11. Interpreter

The interpreter executes JVM bytecode instructions.

For example, conceptually:

```text
JVM bytecode
     ↓
Interpreter
     ↓
CPU instructions
```

The interpreter can start executing code without first compiling the entire application into native machine code.

This helps with startup.

However, repeatedly interpreting frequently executed code is not always the most efficient approach.

---

# 12. Runtime Profiling

While the application is running, the JVM can collect information about program behavior.

For example:

- which methods are executed frequently
    
- which code paths are hot
    
- how often methods are called
    
- which branches are usually taken
    
- what types are actually used
    

This information can be used by the JIT compiler.

Conceptually:

```text
Application
    ↓
Execution
    ↓
Profiling
    ↓
Hot code detected
```

---

# 13. JIT Compilation

**JIT (Just-In-Time) compilation** compiles frequently executed bytecode into native machine code at runtime.

```text
Bytecode
   ↓
Interpreter
   ↓
Profiling
   ↓
Hot method
   ↓
JIT Compiler
   ↓
Native machine code
   ↓
CPU
```

For example, suppose:

```java
for (int i = 0; i < 1_000_000; i++) {
    calculate(i);
}
```

`calculate()` may be executed many times.

The JVM can identify it as **hot code** and compile it into optimized native machine code.

Afterward, execution can use the compiled native code instead of repeatedly interpreting the bytecode.

---

# 14. JIT Optimization

The JIT compiler doesn't necessarily perform a simple:

```text
bytecode → machine code
```

translation.

It can perform runtime optimizations based on observed behavior.

Examples include:

- method inlining
    
- dead code elimination
    
- loop optimizations
    
- escape analysis
    
- devirtualization
    
- speculative optimizations
    

Conceptually:

```text
Bytecode
   ↓
Runtime profiling
   ↓
JIT
   ↓
Optimization
   ↓
Native machine code
```

This is one of the major reasons the JVM can achieve high performance.

See:

`[[JIT]]`

---

# 15. Native Machine Code

Eventually, frequently executed code may exist as native machine code.

For example:

```text
Java bytecode
      ↓
JIT
      ↓
x86-64 instructions
```

or on another machine:

```text
Java bytecode
      ↓
JIT
      ↓
ARM64 instructions
```

The same `.class` file can therefore result in different native machine code depending on the platform.

```text
             Main.class
                 │
        ┌────────┴────────┐
        ▼                 ▼
     x86 JVM           ARM JVM
        │                 │
        ▼                 ▼
   x86 machine        ARM machine
      code                code
```

---

# 16. Important: Bytecode is not machine code

This distinction is critical.

```text
.class
   ↓
JVM bytecode
```

is **not** the same as:

```text
machine code
```

JVM bytecode:

```text
iload
iadd
invokevirtual
return
```

Machine code:

```text
CPU-specific instructions
```

JVM bytecode is designed for the abstract JVM instruction set.

Machine code is designed for a specific CPU architecture.

The complete simplified pipeline is:

```text
                    Java source

                         ▼
                    .class file
                         │
                         ▼
                   Class Loader
                         │
                         ▼
                    Verification
                         │
                         ▼
                      Linking
                  ┌──────┴──────┐
                  │             │
             Preparation    Resolution
                  │             │
                  └──────┬──────┘
                         ▼
                  Initialization
                         │

                    main() starts
                         │
```

# 18. Example

Consider:

```java
public class Main {

    public static void main(String[] args) {
        int a = 10;
        int b = 20;
        int result = a + b;

        System.out.println(result);
    }
}
```

### Step 1 — Source

```text
Main.java
```

### Step 2 — Compilation

```bash
javac Main.java
```

Result:

```text
Main.class
```

### Step 3 — JVM startup

```bash
java Main
```

The JVM starts.

### Step 4 — Class loading

The JVM loads `Main`.

### Step 5 — Verification / linking / initialization

The JVM prepares the class for execution.

### Step 6 — Entry point

The JVM invokes:

```java
main()
```

### Step 7 — Bytecode execution

The JVM executes the bytecode corresponding to:

```java
int result = a + b;
```

### Step 8 — JIT

If some code becomes sufficiently hot, the JVM implementation may compile it into optimized native machine code.

---

# 19. What happens only once vs repeatedly?

A useful mental model:

```text
Application startup
│
├── JVM starts
├── Classes are loaded
├── Classes are linked
├── Classes are initialized
└── main() starts
        │
        ▼
Application execution
        │
        ├── Bytecode execution
        ├── Profiling
        ├── JIT compilation
        ├── Garbage collection
        └── More class loading when needed
```

Not everything happens once.

For example, classes can be loaded lazily as they become necessary.

JIT compilation happens during runtime.

Garbage collection can happen repeatedly during the lifetime of the application.

---

# 20. The most important distinction

Do not memorize the pipeline as:

```text
Java → JVM → CPU
```

The more accurate mental model is:

```text
.java
  │
  │ Java compiler
  ▼
.class
  │
  │ JVM loads
  ▼
JVM runtime
  │
  ├── verification
  ├── linking
  ├── initialization
  ├── interpretation
  ├── profiling
  └── JIT compilation
          │
          ▼
   machine code
          │
          ▼
         CPU
```

The key idea:

> **Java source code is compiled into JVM bytecode. The JVM loads and prepares that bytecode, executes it, and a JVM implementation may use JIT compilation to turn frequently executed bytecode into optimized native machine code.**
