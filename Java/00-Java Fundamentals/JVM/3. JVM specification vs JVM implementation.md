# JVM Specification vs JVM Implementation

## 1. The basic idea

The easiest way to understand the JVM is to separate two things:

> **JVM Specification = what a JVM must do.**  
> **JVM Implementation = how a particular JVM actually does it.**

This distinction is fundamental. A lot of JVM explanations become confusing because they mix concepts from the **Java Virtual Machine Specification (JVMS)** with implementation details of a particular JVM, most commonly **HotSpot**.

The official JVMS defines the abstract machine: its class-file format, instruction set, runtime data areas, execution semantics, class loading, linking, initialization, and other required behavior.

A JVM implementation is a real piece of software that implements this specification.

For example:

```text
                    JVM Specification
                           │
                    defines the contract
                           │
             ┌─────────────┼─────────────┐
             ↓             ↓             ↓
          HotSpot        OpenJ9        Other JVM
             │             │             │
             └─────────────┼─────────────┘
                           ↓
                  concrete implementation
```

The important consequence is:

> **The specification defines the required semantics, not necessarily the internal mechanism used to achieve them.**

---

# 2. What exactly is the JVM Specification?

The **Java Virtual Machine Specification (JVMS)** is a formal specification of an abstract machine.

The current Java SE 23 specification, for example, contains chapters describing the JVM structure, runtime data areas, instruction set, class-file format, verification, loading, linking, initialization, and execution.

The JVM specification defines things such as:

- the `.class` file format;
    
- primitive and reference types;
    
- the JVM instruction set;
    
- the operand stack;
    
- local variables;
    
- frames;
    
- runtime data areas;
    
- heap semantics;
    
- method area;
    
- run-time constant pool;
    
- class loading;
    
- linking;
    
- initialization;
    
- bytecode verification;
    
- method invocation;
    
- exceptions;
    
- synchronization.
    

For example, the JVMS defines instructions such as:

```text
iload
istore
iadd
invokevirtual
invokestatic
new
getfield
putfield
athrow
monitorenter
monitorexit
```

These are part of the JVM's abstract instruction set.

The specification therefore gives different JVM implementations a common target.

---

# 3. Why do we need a specification?

Imagine that Java had only one JVM implementation.

Suppose Oracle's JVM decided:

```text
.class files have this format
bytecode behaves this way
objects behave this way
method invocation works this way
```

and there were no specification.

Then another company wanting to create a JVM would have to reverse-engineer the first implementation.

That would be terrible for portability.

Instead, Java defines a contract:

```text
                    JVMS
                     │
          ┌──────────┼──────────┐
          ↓          ↓          ↓
       HotSpot      OpenJ9     Other JVMs
          │          │          │
          └──────────┼──────────┘
                     ↓
          same required semantics
```

As long as an implementation follows the specification, Java bytecode can be executed by that implementation.

This is one of the important reasons for the JVM's portability.

---

# 4. JVM Specification is not the JVM itself

This distinction is worth remembering.

The JVMS is a **document**.

The JVM implementation is **software**.

For example:

```text
JVMS
 │
 │ specification
 ↓
"Here is what invokevirtual means."

HotSpot
 │
 │ implementation
 ↓
"Here is the code and machinery I use
to implement invokevirtual."
```

The specification does not contain the complete source code of HotSpot.

It defines the behavior that an implementation must provide.

---

# 5. What is a JVM implementation?

A JVM implementation is an actual program capable of executing JVM bytecode according to the JVM specification.

Examples include:

- **HotSpot**
    
- **OpenJ9**
    
- **GraalVM-based JVM implementations**
    

HotSpot is developed as part of OpenJDK. The OpenJDK HotSpot documentation describes components such as the class-loading subsystem, bytecode interpreter, runtime system, JIT compilers, garbage collectors, synchronization mechanisms, and other internal subsystems.

So when we say:

> "The JVM uses G1."

we should immediately ask:

> **Which JVM implementation?**

G1 is not a requirement imposed by the JVM specification. It is a garbage collector implemented by HotSpot.

Likewise:

> "The JVM has Metaspace."

This statement is too vague.

A more precise statement is:

> **HotSpot uses Metaspace to manage class metadata.**

Metaspace is a HotSpot implementation component, whereas the JVMS specifies the abstract **Method Area**. OpenJDK's HotSpot documentation explicitly describes Metaspace as HotSpot's native-memory manager for class metadata.

---

# 6. Specification vs implementation: the most important distinction

Consider the **heap**.

The JVMS defines the heap as a runtime data area from which memory for class instances and arrays is allocated. The specification describes its required behavior, but does not dictate a particular garbage-collection algorithm or physical memory layout.

Therefore:

```text
JVMS:
    Heap
      ↓
    abstract concept + required semantics

HotSpot:
    Heap
      ↓
    specific memory-management implementation
      ↓
    G1 / ZGC / Serial / Parallel / etc.
```

The specification says **what must be true**.

The implementation decides **how to make it true**.

This pattern appears everywhere in the JVM.

---

# 7. Runtime Data Areas

The JVMS defines several runtime data areas.

Conceptually:

```text
JVM Runtime Data Areas

├── PC Register
├── JVM Stacks
├── Heap
├── Method Area
├── Run-Time Constant Pool
└── Native Method Stacks
```

These are specified concepts. The JVMS has dedicated sections describing them.

However, we should not automatically assume that each specification concept corresponds to one obvious physical memory region in a particular JVM.

For example:

```text
Specification:
    Method Area

HotSpot:
    Metaspace and associated internal structures
```

The **Method Area** is part of the abstract JVM model.

**Metaspace** is an implementation detail of HotSpot.

Confusing these two is a common JVM-learning mistake.

---

# 8. The Method Area vs Metaspace

This deserves special attention.

The JVM specification defines the **Method Area** as a runtime data area associated with the JVM. It stores structures related to classes, methods, fields, and other class-level information.

But the specification does not say:

> "Create a memory region called Metaspace."

That is HotSpot terminology.

HotSpot's current implementation uses **Metaspace**, which is a native-memory manager for class metadata.

Therefore:

```text
                JVMS
                 │
                 ↓
            Method Area
                 │
          abstract concept
                 │
                 ↓
              HotSpot
                 │
                 ↓
             Metaspace
```

This is an excellent example of specification vs implementation.

---

# 9. JVM Stack vs physical memory

The same principle applies to the JVM Stack.

The specification defines a **JVM stack** for each JVM thread. It describes stack frames and their contents, including local variables and the operand stack.

For example, conceptually:

```text
Thread
  │
  ↓
JVM Stack

┌──────────────────────┐
│ Frame: methodC()     │
├──────────────────────┤
│ Frame: methodB()     │
├──────────────────────┤
│ Frame: methodA()     │
└──────────────────────┘
```

Each frame can contain:

```text
Local Variables
Operand Stack
Reference to Runtime Constant Pool
```

But the specification does not require an implementation to represent every abstract concept in exactly the way you might draw it in a diagram.

The physical representation is an implementation concern.

Therefore, avoid saying:

> "The JVM specification says the JVM stack is a specific contiguous memory structure."

That's too strong.

A better statement is:

> **The JVMS defines the logical behavior and contents of JVM stacks and frames; the implementation determines their physical representation.**

---

# 10. Interpreter and JIT Compiler

One of the clearest examples of implementation freedom is bytecode execution.

The JVM specification defines bytecode instructions and their semantics.

For example:

```text
iadd
```

means an integer addition operation on values on the operand stack.

But the specification does not require the JVM to literally execute every bytecode instruction through a simple interpreter.

An implementation can use:

```text
Bytecode
   ↓
Interpreter
   ↓
profiling
   ↓
JIT compiler
   ↓
native machine code
   ↓
CPU
```

HotSpot, for example, has an interpreter and JIT compilers. OpenJDK's HotSpot documentation explicitly describes the interpreter and multiple compiler components.

The JVM specification cares about the **observable result**, not whether HotSpot used interpretation or native code generation to obtain it.

This is a crucial idea:

> **The JVM specification specifies the semantics of execution, not one mandatory execution strategy.**

---

# 11. Garbage Collection

Garbage collection is another excellent example.

A common beginner statement is:

> "JVM uses Garbage Collector."

This is broadly true, but technically incomplete.

The specification defines the heap and the semantics associated with memory management, but it does not mandate one particular garbage-collection algorithm.

An implementation can use different collectors.

HotSpot has implemented multiple collectors, including:

```text
Serial
Parallel
G1
ZGC
```

and others over its history.

Therefore:

```text
JVMS
 │
 └── Heap semantics
          │
          ↓
     JVM implementation
          │
          ├── G1
          ├── ZGC
          ├── Serial
          └── ...
```

This is why two JVM implementations can have radically different memory-management internals while still implementing the same JVM specification.

---

# 12. Object layout

Another important example is object layout.

The JVM specification talks about objects and references.

But it does **not** prescribe a universal physical object layout such as:

```text
Object:
┌─────────────────┐
│ Mark Word       │
├─────────────────┤
│ Klass Pointer   │
├─────────────────┤
│ Fields          │
├─────────────────┤
│ Padding         │
└─────────────────┘
```

That kind of diagram usually describes a **particular JVM implementation**, especially HotSpot.

Things such as:

- object headers;
    
- mark words;
    
- compressed ordinary object pointers;
    
- compressed class pointers;
    
- field layout;
    
- alignment;
    
- object size;
    

are implementation details rather than universal JVMS requirements.

So if you see an article saying:

> "Every Java object has an 8-byte mark word."

be suspicious.

The correct question is:

> **In which JVM implementation, architecture, and configuration?**

This habit will save you from a lot of garbage JVM information on the Internet.

---

# 13. Class loading

Class loading is another area where the distinction matters.

The JVM specification defines the concepts of:

```text
Loading
   ↓
Linking
   ├── Verification
   ├── Preparation
   └── Resolution
   ↓
Initialization
```

The specification describes the required behavior of these phases.

A concrete JVM then implements those mechanisms.

For example, HotSpot has its own class-loading subsystem and internal representations. OpenJDK documentation explicitly describes HotSpot's implementation of class loading, linking, and initialization according to the JVMS.

Therefore:

```text
JVMS:
    defines class-loading semantics

HotSpot:
    implements those semantics
    using its own internal data structures
    and algorithms
```

---

# 14. Class file format is specified

One of the areas where the JVM specification is very concrete is the **class-file format**.

The JVMS defines structures such as:

```text
ClassFile
 ├── magic
 ├── minor_version
 ├── major_version
 ├── constant_pool
 ├── access_flags
 ├── this_class
 ├── super_class
 ├── interfaces
 ├── fields
 ├── methods
 └── attributes
```

The specification also defines the constant pool and its different entry types, such as:

```text
CONSTANT_Class
CONSTANT_Fieldref
CONSTANT_Methodref
CONSTANT_String
CONSTANT_Integer
CONSTANT_Long
CONSTANT_NameAndType
CONSTANT_Utf8
CONSTANT_MethodHandle
CONSTANT_InvokeDynamic
...
```

These structures are part of the standardized class-file format.

This is why a `.class` file generated by `javac` can be consumed by different JVM implementations.

---

# 15. Bytecode is specified

The JVM also has a standardized instruction set.

For example:

```java
int result = a + b;
```

can be represented using bytecode instructions involving loading values and performing `iadd`.

The JVM specification defines the semantics of instructions such as:

```text
iload
istore
iadd
imul
new
getfield
putfield
invokevirtual
invokestatic
return
athrow
```

The JVM implementation is responsible for actually executing those instructions.

So:

```text
Bytecode instruction
        │
        ↓
JVMS defines meaning
        │
        ↓
Implementation decides mechanism
        │
        ├── interpreter
        ├── JIT-generated native code
        └── other implementation techniques
```

---

# 16. The JVM does not have to be implemented in Java

Another misconception is:

> "Because it is the Java Virtual Machine, it must be written in Java."

No.

A JVM implementation can be written largely in languages such as C++, C, Rust, or other implementation languages.

HotSpot itself contains a large native codebase; OpenJDK documents its C/C++ implementation and separate runtime/compiler/GC components.

The JVM is a **virtual machine specification**, not a requirement about the programming language used to implement the virtual machine.

---

# 17. JVM specification vs Java Language Specification

There is another distinction that is extremely important:

```text
JLS ≠ JVMS
```

### Java Language Specification — JLS

The **JLS** defines the Java programming language.

It describes things such as:

```java
class User {
    private int age;

    public void setAge(int age) {
        this.age = age;
    }
}
```

The JLS defines what this Java source code means.

### Java Virtual Machine Specification — JVMS

The **JVMS** defines the virtual machine and its class-file/bytecode execution model.

The compiler transforms Java source code into class files:

```text
Java source
     │
     │ javac
     ↓
.class file
     │
     │ JVM
     ↓
execution
```

So:

```text
JLS
 ↓
Java language semantics

javac
 ↓
compiler

JVMS
 ↓
class-file + bytecode + JVM semantics

JVM implementation
 ↓
actual execution
```

The JLS and JVMS are therefore different specifications with different responsibilities.

---

# 18. A concrete example

Consider:

```java
public int sum(int a, int b) {
    return a + b;
}
```

There are several layers.

### Layer 1 — Java language

The JLS defines:

```text
int
+
method
return
parameters
```

and their semantics.

### Layer 2 — Compiler

`javac` translates the source into a `.class` file.

Conceptually, the method could contain bytecode similar to:

```text
iload_1
iload_2
iadd
ireturn
```

### Layer 3 — JVM specification

The JVMS defines what those instructions mean.

For example:

```text
iload_1
```

loads a value from a local-variable slot onto the operand stack.

```text
iadd
```

takes integer values from the operand stack and produces their sum.

```text
ireturn
```

returns the integer result.

### Layer 4 — JVM implementation

HotSpot can execute that bytecode through its interpreter or compile frequently executed code into native machine instructions using JIT compilation.

Therefore:

```text
Java source
     ↓
    JLS
     ↓
   javac
     ↓
.class / bytecode
     ↓
    JVMS
     ↓
JVM implementation
     ↓
machine code / execution
     ↓
   CPU
```

This is the complete picture.

# 19. What is standardized and what is implementation-specific?

A useful classification is:

|Concept|Specification or implementation?|
|---|---|
|`.class` file format|**JVMS**|
|Bytecode instructions|**JVMS**|
|Operand stack semantics|**JVMS**|
|Local variables in frames|**JVMS**|
|JVM Stack concept|**JVMS**|
|Heap concept|**JVMS**|
|Method Area concept|**JVMS**|
|Runtime Constant Pool|**JVMS**|
|Class loading semantics|**JVMS**|
|Verification|**JVMS**|
|Metaspace|**HotSpot implementation**|
|G1|**HotSpot implementation**|
|ZGC|**HotSpot implementation**|
|Object header layout|**Implementation-specific**|
|Mark Word|**HotSpot implementation concept**|
|Compressed Oops|**HotSpot implementation**|
|Exact object layout|**Implementation-specific**|
|JIT implementation|**Implementation-specific**|
|Interpreter implementation|**Implementation-specific**|
|Internal GC algorithms|**Implementation-specific**|
|Internal class metadata structures|**Implementation-specific**|

The key is not that the right-hand column is somehow "less real."

It is real—but it is **not universally required by the JVMS**.

# 20. Public behavior vs private implementation

A useful way to think about the entire JVM is:

```text
                PUBLIC CONTRACT
              ┌─────────────────┐
              │      JVMS       │
              │                 │
              │ Required        │
              │ behavior        │
              └────────┬────────┘
                       │
                       ↓
             PRIVATE IMPLEMENTATION
              ┌─────────────────┐
              │    HotSpot      │
              │                 │
              │ Algorithms      │
              │ Data structures │
              │ Memory layout   │
              │ JIT             │
              │ GC              │
              └─────────────────┘
```

The implementation has freedom as long as it does not violate the required semantics.

This is why the JVMS itself contains a section titled **"Public Design, Private Implementation."**

That section captures an important philosophy of the JVM specification:

> The specification describes the externally relevant architecture while allowing implementations freedom in their internal design.

---

# 21. Why this distinction matters to a Java developer

At first, this may seem like academic terminology.

It isn't.

Suppose you are debugging a memory problem.

You read:

> "Objects are stored in the heap."

That's useful.

But then you read:

> "The heap consists of Eden, two Survivor spaces, and Old Generation."

Now you need to ask:

> **Which JVM and which GC?**

That's no longer a universal JVM statement.

For HotSpot with a particular collector, this may be meaningful.

For another collector or another JVM implementation, the internal organization can be completely different.

The same applies to:

```text
Metaspace
Compressed Oops
Object headers
Mark Word
TLABs
Card tables
Remembered sets
Safepoints
JIT tiers
Code Cache
GC regions
```

These are increasingly implementation-specific concepts.

# 22. A practical rule for reading JVM articles

Whenever you read something about the JVM, classify the statement.

Ask:

### Question 1

**Is this defined by the JVMS?**

If yes:

```text
Specification-level knowledge
```

Example:

> `invokevirtual` has defined JVM semantics.

### Question 2

**Is this specific to HotSpot?**

If yes:

```text
Implementation-level knowledge
```

Example:

> HotSpot has G1 and ZGC.

### Question 3

**Is this specific to a particular JVM version/configuration/architecture?**

If yes:

```text
Highly implementation-dependent knowledge
```

Example:

> An object has a particular header size.

This third category is where many outdated JVM articles become garbage.

A statement can be perfectly correct for:

```text
HotSpot
JDK 17
x86-64
specific GC
specific JVM flags
```

and completely wrong when generalized to:

```text
"the JVM"
```

# 23. The most important mental model

Don't imagine the JVM as one concrete program.

Instead, imagine:

```text
                     JVM Specification
                            │
                    abstract machine
                            │
             ┌──────────────┼──────────────┐
             │              │              │
             ↓              ↓              ↓
          HotSpot          OpenJ9       another JVM
             │              │              │
             ↓              ↓              ↓
         own internals   own internals  own internals
             │              │              │
             └──────────────┼──────────────┘
                            ↓
                    executes JVM programs
```

All implementations can have different:

- memory managers;
    
- garbage collectors;
    
- JIT compilers;
    
- object layouts;
    
- internal data structures;
    
- synchronization implementations;
    
- class metadata representations;
    
- optimization strategies.
    

Yet they can still implement the same JVM specification.

---

# 24. The one sentence to remember

If you forget everything else, remember this:

> **The JVM Specification defines the abstract machine and its required behavior; a JVM implementation is a concrete program that chooses the algorithms, data structures, memory layout, and execution techniques used to provide that behavior.**

Or even shorter:

```text
Specification = WHAT
Implementation = HOW
```

That is the core distinction.

# 25. Sources

### Primary sources

- **Java Virtual Machine Specification, Java SE 23** — the authoritative source for JVM architecture, runtime data areas, bytecode, class-file format, verification, loading, linking, initialization, and execution semantics.
    
- **Java Language Specification, Java SE 23** — the authoritative source for the Java programming language itself.
    
- **OpenJDK HotSpot documentation** — useful when moving from the specification into actual HotSpot internals such as class loading, interpretation, runtime components, and memory management.
    
- **OpenJDK HotSpot Metaspace documentation** — useful for understanding the difference between the specification-level Method Area and HotSpot's Metaspace implementation.
    

### Recommended reading order

```text
1. JLS
   ↓
2. JVMS Chapter 2
   ↓
3. JVMS Chapter 4 — Class File Format
   ↓
4. JVMS Chapter 5 — Loading, Linking, Initialization
   ↓
5. JVMS Chapter 6 — Instruction Set
   ↓
6. HotSpot Runtime Overview
   ↓
7. HotSpot source code / internals
```

**Do not start by memorizing HotSpot internals.** First understand the abstract machine defined by the JVMS. Then learn how HotSpot implements it. Otherwise you will end up memorizing HotSpot-specific behavior and incorrectly calling it "how the JVM works."
